DERIVACION DE LAS DEPENDENCIAS

Las relaciones NO se dibujaron por criterio estetico: se derivaron una por una

Dibujar las 33 aristas entre 12 cajas produjo una marana ilegible. Dos intentos
de arreglarlo fallaron:
  - layout_connectors de EA empeoro el resultado: genero diagonales que cruzaban
    todo el lienzo.
  - Cambiar routingStyle por API no limpia los waypoints ya guardados a nivel de
    diagrama.

SOLUCION APLICADA — REDUCCION TRANSITIVA

Como el grafo es aciclico admite reduccion transitiva: el subconjunto minimo de
aristas cuya clausura transitiva es identica a la del grafo completo. Calculada
sobre el grafo real:

    33 dependencias se reducen a 13 aristas, sin perder NINGUNA relacion de
    alcanzabilidad.

Si `ventas` depende de `inventario`, el diagrama lo sigue mostrando por el camino
ventas -> reservas -> inventario. Lo unico que deja de verse es cuales de esas
dependencias son llamadas directas, y eso se recupera con una matriz en el
documento.

Las 13 aristas:

    organizacion   -> seguridad
    catalogo       -> seguridad
    inventario     -> catalogo, organizacion
    probador       -> catalogo
    reservas       -> inventario
    abastecimiento -> inventario
    ventas         -> reservas
    pagos          -> ventas
    entregas       -> ventas
    reportes       -> probador, ventas
    inteligencia   -> reportes

Los 7 niveles resultantes (toda dependencia apunta hacia abajo):

    Nivel 6  Inteligencia   inteligencia
    Nivel 5  Explotacion    reportes, pagos, entregas
    Nivel 4  Transaccion    ventas
    Nivel 3  Operacion      reservas, abastecimiento
    Nivel 2  Recursos       inventario, probador
    Nivel 1  Maestros       catalogo, organizacion
    Nivel 0  Base           seguridad

Se uso change_connector_visibility, que oculta conectores POR DIAGRAMA. El
modelo mantiene las 33 dependencias; el diagrama muestra 13.

Ademas se creo un diagrama nuevo en vez de reutilizar el anterior, porque sus
conectores arrastraban waypoints guardados que no se podian resetear por API.

HALLAZGO CLAVE: LAS IMAGENES EXIGEN CLOUDINARY

La columna producto_imagen.url NO guarda una URL: guarda el public_id de
Cloudinary. La URL final se arma al vuelo con storage.url_catalogo(). El propio
docstring de core/storage.py lo documenta como convencion del proyecto. Por lo
tanto no se puede insertar una URL externa: el sistema la tomaria como public_id
y generaria una direccion rota.

La razon del diseno es buena: como se guarda el identificador y no la URL, se
puede cambiar tamano o formato sin tocar una sola fila (es lo que sostiene el
RNF02 de rendimiento del catalogo).

CONFIGURACION DE CLOUDINARY

DEFECTO ENCONTRADO Y CORREGIDO: IDEMPOTENCIA

La primera version no era idempotente: la segunda corrida agregaba 74 filas de
stock. Causa: el generador de azar era compartido y se desincronizaba, porque
cuando una variante ya tenia stock el `continue` salteaba consumos del generador
y la secuencia elegia otras sucursales.

Correccion: el azar se deriva del SKU de cada variante
(random.Random(variante.sku)) y del par variante-sucursal para los minimos y
maximos. Verificado corriendo el seed cinco veces: las dos ultimas agregaron
cero filas.

DEFECTO ENCONTRADO Y CORREGIDO: DESCARGAS QUE SE CAEN

Una descarga fallo con ConnectionResetError y tumbo toda la preparacion a mitad
de camino. Se agregaron reintentos con espera progresiva (4 intentos). En la
corrida siguiente se recupero solo dos veces.

DEFECTO ENCONTRADO Y CORREGIDO: MITAD DEL CATALOGO SIN FOTO

El catalogo abria mostrando los 25 productos generados, que no tenian imagen
propia (solo la tenian los 25 del dataset, que quedaban mas abajo en la lista).

Correccion: se amplio preparar_dataset.py para cubrir tambien prendas inferiores
(Jeans, Trousers, Track Pants, Shorts) y producir un excedente de imagenes por
categoria (extras.json). seed_demo.py ahora se las asigna a los productos que no
tienen foto, emparejando por categoria. Resultado: 50 de 50 con imagen.

DEFECTO DEL DATASET: METADATA QUE NO CORRESPONDE

Al revisar el catalogo en el navegador aparecio una mujer con saco rotulada como
polera masculina. Se descarto que fuera error propio:
  - La fila del CSV esta bien formada y dice Men / Topwear / Tshirts. El parser
    es correcto.
  - Los 50 archivos tienen hash distinto, asi que no hubo cruce en la descarga.
Conclusion: el dataset declara una prenda y su imagen muestra otra.

Para revisar las 50 sin abrirlas de a una se genero una hoja de contactos con
todas rotuladas por su articleType. Se encontraron 2 errores de 50 (4%):
    1165 - declarado "Men / Tshirts", la imagen es un saco de mujer
    3323 - declarado "Men / Jackets", la imagen es una polera polo

Correccion: se anotaron en IDS_DESCARTADOS dentro de preparar_dataset.py, con la
razon de cada una, para que no vuelvan a salir elegidas. Se bajaron reemplazos
(1588 y 4848), se verifico visualmente que si correspondieran, y se reasignaron
las fotos de los 25 productos generados (borrando tambien las anteriores de
Cloudinary para no dejar huerfanas).

Levantar el sistema
    cd backend
    .venv/Scripts/python -m uvicorn app.main:app --reload --port 8000
    cd ../web
    npm start

    cd backend
    .venv/Scripts/python -m scripts.seed_demo

    .venv/Scripts/python -m scripts.preparar_dataset

    cd "<raiz>/tienda_ropa"

    (cerrar el documento en Word antes: si esta abierto, bloquea la escritura)
